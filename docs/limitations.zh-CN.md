## 编辑、删除与保护

- 删除更新从活动 JSONL 中移除记录。私聊与普通群按账户消息 ID 删除，频道按会话和消息 ID 删除。
- 先保存删除标记，再替换会话文件。重启恢复继续应用标记，避免后续历史响应恢复已删记录。
- 编辑替换旧正文和结构化信息。补拉过程中到达的实时编辑优先于较早的历史响应。
- 跳过带 `ttl_period`、媒体 `ttl_seconds`、保护/限制标志或付费媒体的消息，不先存入再倒计时删除。
- 发现聊天保护时清空其归档并阻止继续保存。自动删除启用更新也触发同样的保守处理。
  远端取消保护不会自动解除本地阻止。
- 启动与周期同步核对已有消息 ID，更新离线编辑并移除删除。
  会话访问权限明确撤销时，清空该会话归档并阻止继续保存。

程序停止、断网或等待 Telegram 限速期间无法观察远端变化，重连后需恢复更新或完成核对。
长时间离线可能超出服务端更新保留范围，无法恢复全部中间状态或短暂存在的消息。

归档器随自己维护的元数据更新 SQLite 媒体索引。
`files` 中已完成下载的记录单独保存，远端删除后继续保留。
JSONL 替换与 SQLite 更新是两个独立写入操作。索引更新失败时归档器停止，
重启后在应用已保存的删除与排除状态的同时，从当前 JSONL 重建媒体映射。
JSONL 仍是消息存储，SQLite 不再复制正文，下载记录也不能恢复已不可访问的消息。

同步周期会保存开始时间、阶段、peer 位置、逐页历史游标、核对游标和 JSONL 替换回执。
重启会继续已保存的周期，不会静默移动时间边界。编辑/删除核对默认回看一小时，
需要完整检查所有保留消息时使用 `--reconcile-window all`。缩短窗口可能有意漏掉更早的远端编辑或删除。

Telegram 更新协议游标与归档周期分开持久化。差分响应会先经过可持久化的归档边界，
再允许上游管理器推进游标；归档回调失败时保留响应以便重试。但 JSONL、两个 SQLite
数据库和 Telegram 内存更新队列仍不是跨文件事务，因此必须依靠周期和回执完成崩溃恢复。

清理仅覆盖本程序管理的活动文件。外部副本、备份、文件系统快照、
已打开的旧文件描述符及磁盘残留不受本程序控制。原子替换不等于安全擦除。

## 下载是主动保存副本

下载前和提交完成文件前，`fetch` 检查删除、保护、自毁及附件身份。
这些检查无法预测下载结束后的删除。保存的文件没有后台删除同步，不是 Telegram 消息的生命周期镜像。
文件留存与备份需要单独管理。
下载成功会写入共享 SQLite 的 `files` 记录，不改写 JSONL 和归档器元数据。
之后移动或删除本地文件时记录不会自动变化，它不是文件系统监视器。

## 账户与进程边界

同一组件数据目录同时仅允许一个进程使用。归档器与下载器需要同一账户的不同会话。
账户不匹配、会话失效或归档/会话/游标写入失败时程序停止，不自动更换账户、授权或应用身份。

### 并行命令与快照语义

`archive` 持有归档数据目录锁，同一目录同时只能有一个归档进程使用。
JSONL 通过临时文件、`fsync` 和原子替换写入。Unix 上运行时库和归档 SQLite 数据库使用 WAL，
Windows 使用 SQLite rollback journal；两者都有十秒 busy timeout，并为每个 store 限制为一个连接；并发 SQLite 事务会等待或超时失败，
不会互相覆盖。

`search` 是离线只读读取器，不获取归档目录锁。它分别读取 JSONL 和 SQLite 元数据，
然后再次核对元数据，因此无法对 JSONL、`state.sqlite` 和 `archive/index.sqlite`
提供一个跨文件事务快照。归档器运行时，搜索可能看到稍旧的视图；如果文件替换恰好跨过
读取边界，也可能报告账户或元数据不一致。它不会写入归档状态。

`fetch` 只锁定自己的下载数据目录，不锁定归档目录。它先读取本地归档快照，再访问 Telegram，
因此可以和 `archive` 并行运行。它只向 `archive/index.sqlite` 的共享 `files` 表写入已完成下载，
不会修改 JSONL 或归档同步元数据；SQLite 事务负责协调这项记录与归档器的写入。
远端消息删除后，本地已完成文件及其记录仍会保留；它们是主动保存的副本，不是 Telegram
消息生命周期的镜像。

复制 JSONL 和 SQLite 作为完整备份前，请停止 `archive` 和 `fetch`。保留 journal 附属文件（Unix 的
`-wal`/`-shm` 或 Windows 的 `-journal`），数据库快照应使用 SQLite backup API。

### 常驻同步

`archive` 始终是常驻服务。它完成一轮历史与删除核对后继续接收实时更新，
在 `--sync-every` 到期或收到更新缺口修复请求后开始下一轮。
`--history-days` 和 `--history-since` 只限制历史分页，不会关闭实时更新，
也不会把程序变成一次性快照。停止服务需要显式信号或不可恢复的同步错误。

`--history-days` 的历史边界会在每个同步周期开始时向前移动。
`--retention-days` 是独立且更长的 JSONL 留存边界，默认值为 `history-days + 5`，
为未完成的补拉留出时间。如果活动 JSONL 内容超过 `--max-storage-bytes`，程序会从最旧记录开始删除；
该参数不会删除 SQLite 状态、会话文件或已完成的下载文件。

对不再出现在当前会话列表中的已归档频道，程序使用保存的 peer access hash
发起一次 `messages.getHistory`、`Limit: 1` 的核验。该检查是惰性的，不会枚举频道成员或用户名。
如果接口只返回管理员权限不足，程序将其视为无法确认，不会阻断频道。

程序不发送聊天消息、不加入群、不标记消息已读。
正常 MTProto 操作仍会改变连接和授权状态，个人账户授权不是服务端强制的只读权限。

非消息、非登录的状态全部保存在 SQLite。旧 JSON 元数据和状态不会导入，
此存储版本请使用新数据目录并保留旧数据。
数据库及 WAL/SHM 或 journal 附属文件均应按私密账户数据保护。
数据库快照应使用 SQLite 备份 API；复制 JSONL 与数据库作为完整归档备份前，
请先停止归档器和下载器。

## 覆盖范围与规模

不支持秘密聊天、服务消息、故事、完整反应详情和投票者名单。
无法恢复已删除、当前无权限或入群前不可见的历史。
群迁移后保留各自普通群与超级群文件，不合并为一个逻辑会话。

该原型将归档索引和消息载入内存，每次变化重写受影响的会话文件，适合验证流程和中小规模归档。
大型或长期归档应使用支持事务更新和删除的存储设计，并明确清理旧快照。

历史补拉使用普通授权请求，未实现 Takeout 会话。
大规模一次性导出可考虑 [Telegram Desktop 导出](https://telegram.org/blog/export-and-more)，
或独立 [Takeout API](https://core.telegram.org/api/takeout) 实现。

本地自动化测试使用模拟输入。一次独立的未授权在线探测已确认 Telegram 接受本项目配置的
应用凭证并返回 `auth.exportLoginToken` 登录令牌；探测没有登录账户或访问消息。
SQLite 流程中的真实账户登录、归档和下载，以及网络重连和服务端更新恢复，仍未完成端到端验证。
